# البنية المعمارية

## نمط البنية: Modular Monolith (وليس Microservices)

**التوصية: تبدأ بـ Modular Monolith** — تطبيق NestJS واحد مقسّم داخليًا لوحدات (Modules) واضحة
الحدود (كما في `apps/api/src/modules/*`)، مو خدمات منفصلة بالكامل من اليوم الأول.

**السبب:** Microservices تحل مشكلة "التوسع المستقل" و"فرق عمل متعددة مستقلة" — وفي مرحلة بناء أولى
بفريق صغير/متوسط، هذا التعقيد (Service discovery, distributed transactions, network latency بين
خدمة المبيعات وخدمة المخزون اللي لازم تتفقا بذرية Atomic) يبطّئ التطوير بدون فائدة حقيقية بعد.
الحدود الواضحة بين الوحدات (Modules) تسمح لك تفصلها لخدمات منفصلة **لاحقًا** لو احتجت فعلاً
(مثلاً وحدة KDS تحتاج تحجيم مستقل لأنها realtime بكثافة عالية).

## خريطة الوحدات (Modules)

```
┌─────────────────────────────────────────────────────────────┐
│                        apps/pos-web (PWA)                    │
│   الكاشير · KDS · إدارة الطاولات · تسوية الوردية              │
└───────────────────────────┬───────────────────────────────────┘
                            │ REST/GraphQL + Sync Queue (offline)
┌───────────────────────────▼───────────────────────────────────┐
│                         apps/api (NestJS)                    │
│                                                                │
│  users        (RBAC, Scope, Auth)                             │
│  branches     (فروع + مطبخ مركزي كـ "location")               │
│  ingredients  (مواد خام + طرق تقييم + دفعات)                  │
│  items        (أصناف مبيعات + BOM/Recipes متعددة المستويات)   │
│  inventory    (أرصدة، جرد، تسويات)                             │
│  purchasing   (موردين، PO، Approval Matrix)                    │
│  production   (أوامر إنتاج، منتجات نصف مصنّعة)                 │
│  transfers    (تحويلات بين المواقع، فاقد نقل)                  │
│  sales        (طلبات، فواتير، ZATCA، عروض، ولاء)               │
│                                                                │
└────────────────────────────────────────────────────────────────┘
                            │
                    PostgreSQL (Prisma)
```

## نقطة التكامل الأهم: Sales ↔ Items ↔ Inventory

هذا هو "قلب" النظام (نفس منطق النموذج الأولي اللي جربناه، لكن بمستوى إنتاجي):

1. عند تأكيد عنصر بالطلب (Order Line)، الـ Backend يقرأ Recipe الخاص بالصنف.
2. لكل مكوّن بالوصفة: إذا كان "مادة خام" يُخصم مباشرة من دفعات المخزون (FIFO أو Weighted Avg
   حسب إعداد الصنف). إذا كان "منتج نصف مصنّع" يُخصم من رصيد ذلك المنتج الوسيط (اللي أُنتج
   بأمر إنتاج سابق) — وليس من مكوناته الخام مباشرة.
3. كل عملية خصم تُسجَّل كـ Stock Movement مستقل (ledger)، **لا يُعدَّل الرصيد مباشرة بدون سجل حركة**
   — هذا ضروري للتدقيق (Audit) ولحساب Food Cost الفعلي لاحقًا.
4. هذه الخطوة يجب أن تكون **atomic** (كلها تنجح أو كلها تفشل) — استخدم DB transaction، ولا تسمح
   بحالة "تم تسجيل البيع لكن فشل خصم المخزون".

## Offline-first: كيف بُنيت فعليًا (`apps/pos-web`)

- `src/offline/db.ts` (Dexie/IndexedDB): يخزّن أصناف المنيو + الوصفات + أرصدة المخزون كنسخة
  محلية (تُحدَّث كل مرة تنجح فيها القراءة أونلاين)، وجدول `localOrders` وهو طابور المزامنة نفسه.
- كل عملية بيع تُكتب محليًا **فورًا** كـ `LocalOrder` بمعرّف عميل (`local_...`) قبل أي محاولة شبكة؛
  الدفع والإلغاء لطلب محلي يُسجَّلان أيضًا كـ "نية معلّقة" (`pendingPayment`/`pendingVoid`) على نفس
  الصف بدل انتظار الشبكة.
- `src/offline/syncEngine.ts` يُعيد تشغيل كل صف غير مكتمل بنفس ترتيب استدعاءات API التي كانت
  ستحدث أونلاين (`POST /orders` ثم `.../pay` ثم `.../void` حسب الحاجة)، عند حدث `online` أو كل 20
  ثانية كشبكة أمان. صف مكتمل تمامًا (أُنشئ + دُفع/أُلغي لو كان مطلوبًا) يُحذف فورًا لأن السيرفر
  بقى المصدر الوحيد للحقيقة عنه.
- **فرق بين خطأ شبكة حقيقي وخطأ سيرفر حقيقي (`api/client.ts`'s `isNetworkError`)**: فشل `fetch`
  نفسه (`TypeError`, لا اتصال) هو الوحيد الذي يُقيَّد -- أي رفض حقيقي من السيرفر (نفاد مخزون فعلي،
  تحقق فشل) **لا يُعاد** آليًا؛ يُعلَّم الصف `sync_failed` مع رسالة الخطأ ويبقى ظاهرًا في لوحة
  الطلبات لمراجعة يدوية، بدل تخمين قرار العمل (منع البيع أو السماح برصيد سالب) الذي تركه هذا
  القسم أصلًا كقرار يحتاج نقاش مع الإدارة.
- الواجهة نفسها (JS/CSS/HTML) تُخدَّم بدون اتصال عبر Service Worker حقيقي
  (`vite-plugin-pwa`, `vite.config.ts`) -- يُخزِّن قالب التطبيق فقط، ولا يتدخل في استدعاءات الـ
  API إطلاقًا (تلك مسؤولية طبقة Dexie أعلاه، عمدًا، للتحكم الصريح بحداثة البيانات). تم التحقق
  فعليًا (Playwright + build إنتاجي حقيقي) أن إعادة تحميل الصفحة بلا اتصال إطلاقًا تعرض شاشة
  تسجيل الدخول من الكاش، لا صفحة فاشلة.
- **الفاتورة الضريبية (ZATCA) الآن مبنية فعليًا (المرحلة 9)**: تُولَّد وتُوقَّع محليًا وقت البيع
  (`OrdersService.pay()` نفسها، لا طابور منفصل -- الفاتورة جزء من نفس الـ DB transaction التي
  تُثبت الدفع)، لكن الرفع الفعلي لمنصة فاتورة لا يزال غير منفَّذ (فجوة اعتماد حكومي حقيقي، لا
  قرار عمل مؤجَّل) -- راجع قسم "ZATCA: كيف بُنيت فعليًا" أدناه للتفاصيل الكاملة.

## ZATCA: كيف بُنيت فعليًا (`apps/api/src/zatca/`)

- `zatca.service.ts`'s `generateForOrder()` يُستدعى من داخل نفس الـ DB transaction لـ
  `OrdersService.pay()` -- الفاتورة تُبنى وتُوقَّع في نفس لحظة تأكيد الدفع (docs/DECISIONS.md #3
  حرفيًا)، لا خطوة لاحقة منفصلة. لو الموقع بلا `vatNumber` مُعدّ، يتخطّى التوليد بصمت (`zatcaSyncStatus`
  يبقى `PENDING`) بدل رفض عملية الدفع نفسها -- إعداد فوترة ناقص لا يجب أبدًا أن يمنع بيعة نقدية حقيقية.
- `invoice-xml.util.ts` يبني فاتورة UBL 2.1 (Simplified Tax Invoice، النوع الغالب لمبيعات
  الكاشير B2C) بالعناصر الأساسية المطلوبة (المورّد + رقمه الضريبي، الإجماليات، سطور الفاتورة).
  هذا بناء هيكلي بحسن نية غير مُتحقَّق منه ضد XSD/Schematron ZATCA الكامل رسميًا -- ذلك يحتاج
  ملفات المخطط الرسمية وفي النهاية بيئة اعتماد ZATCA فعلية للتحقق منه نهائيًا.
- `qr.util.ts` يبني رمز QR بترميز TLV (Tag-Length-Value) + Base64 حسب معيار ZATCA (الوسوم 1-8:
  اسم البائع، الرقم الضريبي، الطابع الزمني، الإجمالي، ضريبة القيمة المضافة، هاش الفاتورة،
  التوقيع، المفتاح العام) مع دالة فك تشفير `decodeQr` مطابقة تمامًا لما يفعله أي قارئ QR حقيقي --
  تُستخدم في الاختبارات للتحقق الدائري (round-trip) الحقيقي، لا مجرد مقارنة نصوص.
- **زوج مفاتيح EC محلي (secp256k1، نفس المنحنى الذي تفرضه ZATCA) يُولَّد تلقائيًا عند أول استخدام**
  ويُحفظ خارج git (`ZATCA_KEYS_DIR`، افتراضيًا `.zatca-keys/`) -- هذا **بديل مؤقت** لشهادة CSID
  حقيقية يُصدرها ZATCA فعليًا عبر بوابة فاتورة (تسجيل + OTP، حتى بيئة الـ Sandbox تحتاجهما ولا
  تتوفر بيانات اعتماد حقيقية من هذه البيئة). التوقيع الناتج تشفيريًا حقيقي وقابل للتحقق فعليًا
  (مُختبر بـ `crypto.verify` الحقيقي في `apps/api/test/zatca.e2e-spec.ts`)، لكنه ليس شهادة
  ZATCA تتعرّف عليها فعليًا -- استبدال هذا الزوج بمفتاح CSID حقيقي لاحقًا هو التغيير الوحيد اللازم.
- `POST /orders/:id/zatca/submit` (الخطوة المنفصلة: رفع الفاتورة الموقّعة فعليًا لمنصة فاتورة)
  **غير منفَّذ عمدًا** -- يُرجع 503 برسالة صريحة بدل تزييف نجاح `SYNCED` لم يحدث فعليًا. تفعيله
  الحقيقي يحتاج: (1) CSID حقيقية من onboarding ZATCA، (2) استبدال المفتاح المحلي أعلاه بمفتاح تلك
  الشهادة، (3) رابط API الرفع الحقيقي (`ZATCA_API_BASE_URL`) -- لا شيء من هذا قابل للتوفير من
  هذه البيئة، فتُرك كخطوة صريحة غير منفَّذة بدل نصف تنفيذ يوهم بالاكتمال.
- 4 اختبارات e2e حقيقية في `apps/api/test/zatca.e2e-spec.ts`: تخطّي التوليد بدون رقم ضريبي (مع
  نجاح الدفع رغم ذلك)، توليد+توقيع حقيقي (XML مُتحقَّق بمحلّل XML حقيقي، الهاش مُعاد حسابه
  ومطابقته، التوقيع مُتحقَّق تشفيريًا ضد المفتاح المخزَّن -- ومُتحقَّق أنه **يفشل** ضد مفتاح مختلف
  لإثبات أن التحقق ليس صحيحًا شكليًا فقط -- والـ QR مُفكَّك ومطابَق حقليًا بحقل)، ثبات الحقول عبر
  `GET /orders/:id`، ورسالة الرفض الصادقة من `submit`.

## KDS: كيف بُنيت فعليًا (`apps/api/src/kitchen/`) -- المرحلة 10a

يغلق هذا فجوة كانت موجودة فعليًا في المخطط منذ السقالة الأصلية: `OrderLine.kitchenStatus`
(القرار #11) و`OrderStatus.READY` كانا معرَّفين لكن غير مستخدَمين إطلاقًا في أي كود حتى الآن.

- `GET /kitchen/queue?locationId=X` يعرض تذاكر المطبخ النشطة فقط -- الطلبات بحالة
  `SENT_TO_KITCHEN` في هذا الموقع، بترتيب الإنشاء (FIFO)، كل تذكرة تحمل رقم الطاولة (لو مرتبطة)
  والقناة وسطورها بحالة تحضير كل سطر على حدة (لا حالة واحدة للطلب كامل -- بالضبط ما ينص عليه
  القرار #11).
- `POST /kitchen/lines/:id/advance` يُقدّم سطرًا واحدًا خطوة واحدة في التسلسل الثابت
  `QUEUED → PREPARING → READY → SERVED` (زر "دفع" واحد لكل سطر، بالضبط كأي شاشة KDS حقيقية --
  لا قافزة حرة بين الحالات). محاولة التقديم بعد `SERVED` تُرفض (400)، وكذلك لأي سطر من طلب
  `VOIDED`.
- **بمجرد وصول كل سطور الطلب لحالة `READY`/`SERVED`، يتحوّل `Order.status` تلقائيًا لـ `READY`**
  (فقط لو كان لا يزال `SENT_TO_KITCHEN` -- لا يتراجع أبدًا عن `PAID`/`VOIDED`) -- هذا أول استخدام
  فعلي لقيمة `READY` في كامل المشروع.
- 5 اختبارات e2e حقيقية في `apps/api/test/kitchen.e2e-spec.ts`: التسلسل الكامل، رفض التقديم بعد
  `SERVED`، رفض التقديم لطلب مُلغى، وتحديدًا إثبات أن الطلب **لا** يتحوّل لـ `READY` إلا بعد أن
  تصل **كل** سطوره لا سطر واحد فقط.
- **القنوات المتعددة (Multi-channel، القرار #10) كانت مكتملة فعليًا منذ المرحلة 3** -- حقل
  `channel` على `Order` موجود ويُستخدم منذ أول يوم (`OrderChannel` enum)، فلا عمل جديد هنا غير
  التأكد من ظهوره في تذاكر المطبخ (أعلاه).
- **متبقٍ من المرحلة 10**: CRM/الولاء (القرار #15) -- `Customer` موجود في المخطط لكن غير مُفعَّل
  في منطق الطلبات بعد (نقاط ولاء).

## Promotions: كيف بُنيت فعليًا (`apps/api/src/promotions/`) -- المرحلة 10b

طبقة حساب منفصلة تمامًا عن التسعير الأساسي (القرار #14 حرفيًا) -- تُحسب فوق `subtotal` قبل
`vatTotal`/`grandTotal`، ولا تُعدَّل عليها إطلاقًا.

- **فقط `PERCENTAGE_DISCOUNT`/`FIXED_DISCOUNT` قابلان للتطبيق فعليًا.** `BOGO`/`COMBO` يبقيان
  قيمتين صالحتين في enum المخطط لعمل مستقبلي، لكن **يُرفض إنشاؤهما من الأساس** (400 عند
  `POST /promotions`) بدل قبول إعداد يبدو محفوظًا بنجاح لكنه لا يُخصم أي شيء فعليًا أبدًا --
  يحتاجان منطق "أصناف مؤهّلة" على مستوى السطر وهو أكبر بكثير من نطاق هذه المرحلة.
- `OrdersService.create()` يُطبِّق العرض **تلقائيًا** فقط لو لم يُرسل الكاشير `discountTotal`
  يدويًا -- الخصم اليدوي يفوز دائمًا (تصميم مقصود: قرار الكاشير الفوري أهم من أتمتة). العرض
  المُطبَّق يُسجَّل في `Order.promotionId` للتدقيق لاحقًا.
- **الترجيح عند تعدد العروض المؤهّلة** يُطابق نفس منطق `ApprovalRulesService.findApplicableRule`
  تمامًا: عرض مخصص لقناة مُحدَّدة يفوز على عرض عام حتى لو خصمه أصغر، وبين عروض بنفس درجة
  التخصيص يفوز الأكبر خصمًا للعميل. الفترة الزمنية (`startsAt`/`endsAt`) والقناة (`channelLimit`)
  يُتحقَّق منهما فعليًا وقت الطلب، لا وقت إنشاء العرض.
- 10 اختبارات e2e حقيقية في `apps/api/test/promotions.e2e-spec.ts`: رفض BOGO/COMBO، رفض نسبة
  >100%، تطبيق تلقائي حقيقي بحساب صحيح، تجاوز الخصم اليدوي للعرض، تجاهل عرض لقناة مختلفة أو خارج
  فترته، الترجيح بنوعيه (تخصيص القناة ثم حجم الخصم)، وتحديد الخصم الثابت بحد الفاتورة نفسها.
- لوحة تحكم (`prototypes/admin_panel.html`, تبويب "🎁 العروض"): إنشاء/عرض/تفعيل-تعطيل، مُتحقَّق
  منها فعليًا بمتصفح حقيقي (Playwright).

## CRM/Loyalty: كيف بُنيت فعليًا (`apps/api/src/customers/`) -- المرحلة 10c

يغلق الفجوة الأخيرة في القرار #15: `Customer.points` كان عدّادًا خامًا بلا أي سجل تدقيق منذ
السقالة الأصلية، رغم أن القرار نفسه ينص صراحة على "Points Ledger منفصل".

- `LoyaltyTransaction` جدول سجل حركة موقّع (نفس منطق `StockMovement` تمامًا: موجب = كسب، سالب =
  استبدال/تعديل + سبب + مرجع اختياري)، و`Customer.points` بقي عدّادًا مجمّعًا **مشتقًا** يُحدَّث
  مع كل حركة في نفس الترانزاكشن -- لا يُعدَّل مباشرة أبدًا بمعزل عن سجل يوثّقه.
- **الكسب يحدث عند الدفع (`OrdersService.pay()`) لا عند إنشاء الطلب** -- طلب قد يُلغى قبل الدفع،
  فمكافأة نقاط على طلب قد يُلغى لاحقًا تكسر التدقيق. المعدّل: نقطة واحدة لكل 10 وحدات عملة من
  `grandTotal` (floor -- بيعة أقل من العتبة تكسب صفرًا لا كسرًا).
  `CustomersService.awardPoints` تُستدعى داخل نفس ترانزاكشن الدفع، بجانب توليد فاتورة ZATCA
  ومنطق العروض -- كلها إضافات مستقلة على نفس الحدث دون أن تتزاحم.
  `customerId` غير الموجود يُرفض الآن صراحة عند إنشاء الطلب (400) بدل الاصطدام بخطأ FK قبيح لاحقًا
  -- أول مرة يُتحقَّق منها فعليًا رغم وجود الحقل منذ المرحلة 3.
- **الاستبدال (`POST /customers/:id/redeem`) عملية مستقلة تمامًا عن إنشاء الطلب** -- لا يُدمَج
  تلقائيًا في خصم الطلب (بعكس محرك العروض)، بل يُرجع القيمة النقدية المكافئة (0.10 وحدة عملة لكل
  نقطة) ليطبّقها الكاشير يدويًا كخصم على الطلب التالي -- قرار تصميم متعمّد لتجنّب تعقيد التفاعل
  مع محرك العروض في هذه المرحلة. يُرفض الاستبدال لو تجاوز رصيد العميل الفعلي.
- 8 اختبارات e2e حقيقية في `apps/api/test/customers.e2e-spec.ts`: رفض جوال مكرر، رفض `customerId`
  غير موجود، عدم لمس السجل إطلاقًا لطلب بلا عميل، حساب الكسب الصحيح مع سطر سجل حقيقي، تراكم النقاط
  عبر عدة طلبات، استبدال ضمن الرصيد وخارجه، والبحث بجزء من رقم الجوال.
- لوحة تحكم (`prototypes/admin_panel.html`, تبويب "👤 العملاء"): إنشاء/بحث/عرض تفاصيل + سجل نقاط،
  مُتحقَّق منها فعليًا بمتصفح حقيقي.
- **بهذا اكتملت المرحلة 10 بالكامل** (10a KDS + 10b Promotions + 10c CRM/Loyalty).

- كل تقرير مُرشَّح بنفس قاعدة الـ Scope المستخدمة في كل وحدة أخرى (`scopedLocationIds`) -- مدير
  فرع يرى أرقام فرعه فقط، وكل المسارات محمية خلف صلاحية جديدة `analytics.view` (بخلاف عمليات
  الكاشير الأساسية التي لا تحتاج صلاحية -- أرقام الإيراد والهامش حسّاسة تجاريًا).
- `GET /analytics/sales-summary` و`GET /analytics/top-items`: إيراد/صافي مبيعات/ضريبة/خصومات/عدد
  طلبات/متوسط الطلب + توزيع حسب القناة، والأصناف الأكثر مبيعًا بالكمية والإيراد -- كلها من طلبات
  `PAID` فقط، بفلترة اختيارية بالموقع وفترة زمنية (`paidAt`، لا `createdAt`).
- **`GET /analytics/food-cost` -- أهم تقرير في هذه المرحلة**: تكلفة البضاعة المباعة (COGS) محسوبة
  من **التكلفة الفعلية الحقيقية** لكل حركة `StockMovement` بسبب `SALE` (كل حركة مرتبطة بدفعة
  `InventoryBatch` بعينها بتكلفتها الحقيقية وقت الاستهلام -- لا تقدير نظري من الوصفة). نسبة تكلفة
  الطعام = COGS ÷ صافي المبيعات، وهامش الربح = الفرق -- المؤشر الأساسي لأي مطعم حقيقي، ومبني هنا
  على بيانات مُدقَّقة فعليًا لا تقريبية.
- `GET /analytics/inventory-valuation`: قيمة المخزون الحالي = Σ (كمية الدفعة × تكلفة وحدتها) لكل
  خامة، تعكس تلقائيًا أي استهلاك حقيقي حدث (دفعة استُهلك جزء منها تنخفض كميتها المتبقية فقط، لا
  تكلفة وحدتها). `GET /analytics/low-stock`: مقارنة مباشرة لكل رصيد بحد `Ingredient.lowStockThreshold`
  الخاص به.
- 9 اختبارات e2e حقيقية في `apps/api/test/analytics.e2e-spec.ts`: تُبنى على بيع حقيقي واحد بأرقام
  معروفة (يستهلك كمية محددة من دفعة بتكلفة معروفة) وتتحقق من كل رقم حسابيًا بالضبط -- شاملة عزل
  الموقع الآخر فعليًا (لا مجرد تجاهل الفلتر)، واستبعاد طلب أُرجع تاريخه خارج نطاق `from`/`to`
  المطلوب (تعديل `paidAt` فعليًا لا محاكاة للساعة)، ورفض تاريخ غير صالح.
- لوحة تحكم (`prototypes/admin_panel.html`, تبويب "📊 التقارير"): فلترة بالموقع والفترة، بطاقات
  ملخص المبيعات وتكلفة الطعام، جداول الأصناف الأكثر مبيعًا وتقييم المخزون وتنبيهات النقص --
  مُتحقَّق منها فعليًا بمتصفح حقيقي.
- **بهذا اكتملت خطة التنفيذ الأصلية بالكامل (المراحل 0-11)**. أي عمل تالٍ (لوحات تحكم تفاعلية
  أعمق، تكامل ZATCA الفعلي عند توفر بيانات اعتماد، إلخ) هو تكرار جديد فوق أساس عملياتي مستقر
  ومُختبر بالكامل، لا استكمال لمرحلة ناقصة. أول تكرار من هذه -- تقارير مجدولة + تصدير Excel/PDF --
  مبني فعلًا الآن، مفصَّل تحت.

### تكرار ما بعد خطة التنفيذ: تقارير مجدولة + تصدير Excel/PDF (`apps/api/src/reports/`)

- `ReportsService` يبني "حزمة" واحدة لكل موقع (أو حزمة إجمالية لكل المواقع) من نفس أربع طرق
  `AnalyticsService` بالضبط (ملخص مبيعات، أصناف أكثر مبيعًا، تكلفة طعام، تنبيهات نقص) -- لا منطق
  حسابي مكرَّر، `ReportsService` طبقة عرض/تصدير فقط فوق `AnalyticsModule` (المُصدَّر الآن من
  `AnalyticsModule.exports`).
- **فصل الطرق حسب المستدعي، لا تكرار الاستدعاء**: كل تقرير في `AnalyticsService` انقسم إلى ثلاث
  طبقات -- `*Core(ids, ...)` (المنطق الفعلي، يأخذ فلتر مواقع مُحلَّل مسبقًا)، طريقة عامة
  `*(userId, ...)` (تُستخدم من `AnalyticsController` لطلبات المستخدمين، تحلّل Scope المستخدم أولًا)،
  وطريقة عامة جديدة `*ForLocation(locationId, ...)` (تُستخدم حصريًا من `ReportsService`، تتجاوز حل
  Scope المستخدم تمامًا). هذا لتفادي خطأ حقيقي كان موجودًا في المسودة الأولى: مهمة نظامية (الـ
  Cron أدناه) لا يوجد لها "مستخدم حالي" على الإطلاق، فاستعارة Scope أي مستخدم عشوائي (حتى لجلب
  `userId` فقط) كانت ستُقيِّد أو تمنع (403) تقرير نظامي يُفترض أن يكون بلا قيود بسبب صلاحيات ذلك
  المستخدم العشوائي تحديدًا.
- **التصدير**: Excel عبر `exceljs` (4 أوراق: ملخص المبيعات، الأصناف الأكثر مبيعًا، تكلفة الطعام،
  نقص المخزون -- كل التسميات والبيانات عربية بالكامل، لأن `exceljs` يكتب نصوص UTF-8 فقط ومحرك
  العرض في Excel نفسه يتولى التشكيل/الاتجاه بلا أي عمل إضافي)، وPDF عبر `pdfkit` (import بصيغة
  `import X = require('pdfkit')` وليس `import X from 'pdfkit'` -- الحزمة `export =` من نوع
  CommonJS، وإعداد TypeScript هنا بلا `esModuleInterop`، فالصيغة الافتراضية كانت ستمر فحص الأنواع
  لكنها تفشل وقت التشغيل). **قيد معروف وموثَّق صراحة في الكود**: `pdfkit` لا يعمل تشكيل حروف عربي
  ولا ترتيب RTL -- يرسم أي Unicode كرموز منفصلة بترتيب الإدخال فقط، ولا توجد أداة عرض/تحويل PDF
  بصري في هذه البيئة (`poppler-utils` تعذّر تثبيتها) للتحقق من أي حل بديل (`arabic-reshaper` مثلاً)
  قبل شحنه -- فالتسميات الهيكلية في PDF إنجليزية عمدًا، وبيانات الموقع/الصنف العربية لا تزال تُطبع
  بخط عربي حقيقي مُضمَّن (`assets/fonts/NotoSansArabic.ttf`) فتظهر كرموز عربية حقيقية لا مربعات
  فارغة، لكن بلا ضمان اتصال الحروف الصحيح. Excel هو الصيغة الصحيحة عربيًا بالكامل لأي استخدام فعلي.
- **التخزين**: `GeneratedReport` (حقل `fileData: Bytes`/`bytea`) يخزّن الملف مباشرة في Postgres --
  قرار مقصود بالنظر لحجم الملفات الصغير المتوقَّع (كيلوبايتات) ولعدم توفر بيانات اعتماد تخزين سحابي
  حقيقية في هذه البيئة (نفس فئة قيد ZATCA/البريد الإلكتروني الخارجية).
- `POST /reports/generate` (فوري، حسب فلتر مستخدم حقيقي + Scope)، `POST /reports/generate-all`
  (نفس منطق الجدولة الآلية أدناه لكن عند الطلب، بلا انتظار الساعة)، `GET /reports` (قائمة، مفلترة
  بـ Scope)، `GET /reports/:id/download` (الملف الفعلي، `StreamableFile`) -- كلها خلف صلاحية
  `analytics.view` نفسها (نفس حساسية أرقام الإيراد/الهامش).
- **الجدولة**: `@Cron('0 1 * * *')` (`@nestjs/schedule`, مُفعَّل عبر `ScheduleModule.forRoot()` في
  `AppModule`) يولّد يوميًا الساعة 1 صباحًا حزمة أمس لكل فرع نشط + حزمة إجمالية، بصيغتَي الملفين
  معًا. "مجدولة" تعني "تُولَّد تلقائيًا وتصير متاحة للتحميل من اللوحة الإدارية" فقط -- لا يوجد إرسال
  بريد إلكتروني فعلي (`scheduledDailyGeneration` معلَّق عليها توضيح ذلك)، لعدم توفر بيانات اعتماد
  SMTP/مزوّد بريد حقيقية في هذه البيئة.
- 7 اختبارات e2e حقيقية في `apps/api/test/reports.e2e-spec.ts`: تتحقق من محتوى الملفات الفعلية لا
  مجرد نجاح الاستجابة -- XLSX يُعاد تحميله وقراءته بـ `exceljs` والتحقق من قيم خلايا محددة تطابق
  بيعًا حقيقيًا بأرقام معروفة، PDF يُحلَّل نصيًا بـ `pdf-parse` والتحقق من وجود الأرقام نفسها في
  النص المستخرَج، إضافة لاختبارات Scope الموقعي (403 خارج النطاق) و`generateForAllLocations` (يُنتج
  (1 + عدد المواقع النشطة) × 2 صف بالضبط).
- لوحة تحكم (`prototypes/admin_panel.html`, تبويب "📊 التقارير", قسم "تصدير التقارير"): توليد فوري
  بأي صيغة (يستخدم نفس فلتر الموقع/الفترة الموجود بالفعل)، زر توليد دفعة اليوم لكل الفروع يدويًا
  (يشغّل نفس منطق الـ Cron بلا انتظار الساعة)، قائمة التقارير المولَّدة + تحميل فعلي (fetch خام +
  `blob()` بدل مسار `api()` العام الذي يفترض JSON دائمًا، ثم رابط `<a download>` مؤقت يُشغّل حوار
  حفظ المتصفح) -- مُتحقَّق منه فعليًا بمتصفح حقيقي.
