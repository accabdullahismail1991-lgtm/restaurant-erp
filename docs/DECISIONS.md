# قرارات التصميم المعمارية

نتيجة جلسة تحليل متطلبات كاملة (grill-me). كل قرار هنا يؤثر على بنية قاعدة البيانات أو الكود
بشكل جوهري، ولذلك تم حسمها قبل كتابة أي كود.

| # | البند | القرار | الأثر التقني |
|---|---|---|---|
| 1 | النطاق | سلسلة فروع بعلامة تجارية واحدة | Multi-branch من الأساس، ليس single-tenant بسيط |
| 2 | الاتصال | Offline-first مع مزامنة | كل فرع يحتاج قاعدة بيانات محلية + طابور مزامنة (Sync Queue) |
| 3 | الضرائب | متوافق مع ZATCA بالكامل (Phase 2) | توليد فاتورة + توقيع رقمي محليًا، ثم رفع لمنصة فاتورة عند توفر الاتصال |
| 4 | الوصفات | Multi-level BOM + أوامر إنتاج | جدول Recipe يدعم مكوّن = مادة خام **أو** منتج نصف مصنّع (self-reference) |
| 5 | موقع الإنتاج | Hybrid (مطبخ مركزي + تحضير محلي) | حقل "موقع الإنتاج" في Production Order مرن، ليس مقفولاً على موقع واحد |
| 6 | التحويلات | دورة كاملة: إرسال → استلام → فاقد نقل | Transfer له حالتان: Dispatched / Received، والفرق بينهما = Transit Loss تلقائي |
| 7 | المشتريات | Hybrid (مركزي للاستراتيجي، محلي للطازج) | صلاحية شراء الصنف تُحدَّد على مستوى الصنف (Item-level purchasing rules) |
| 8 | الموافقات | Approval Matrix حسب القيمة والمصدر | جدول Approval Rules منفصل، غير مبرمج (hardcoded) داخل منطق PO |
| 9 | تقييم المخزون | لكل صنف طريقته (Weighted Avg أو FIFO) | حقل valuation_method على مستوى Ingredient + تتبع دفعات إلزامي (Batch/Lot) لكل المخزون بغض النظر عن الطريقة |
| 10 | القنوات | Multi-channel (فرع + توصيل خارجي + تطبيق) | حقل channel على مستوى Order من اليوم الأول |
| 11 | المطبخ | KDS رقمي | Order Items لها حالة تحضير منفصلة لكل عنصر (per line item status)، ليست حالة واحدة للطلب كامل |
| 12 | النقدية | تسوية وردية كاملة (Cash Reconciliation) | جدول Shifts منفصل بربط Opening/Closing float لكل طريقة دفع |
| 13 | الصالة | إدارة طاولات كاملة (Split bill، نقل، دمج) | Order مرتبط اختياريًا بـ Table، ويدعم علاقة Many-to-many مؤقتة عند الدمج |
| 14 | التسعير | محرك عروض مرن | Promotions Engine منفصل عن التسعير الأساسي، يُطبَّق كطبقة حساب على الفاتورة |
| 15 | العملاء | CRM + Loyalty مدمج | Customer مرتبط اختياريًا بكل Order، مع Points Ledger منفصل |
| 16 | الصلاحيات | RBAC مرن مع Scope | Role غير مبرمج ثابت، بل جدول Permissions × Roles مع scope (branch/region/org) |
| 17 | الأجهزة | تابلت/PWA + جهاز دفع مستقل | Frontend PWA بدل تطبيق أصلي مرتبط بهاردوير معيّن |
| 18 | الدفع | Integrated + Manual (إعداد لكل جهاز) | PaymentTerminal له حقل mode (integrated/manual) |
| 19 | الجرد | جرد دوري كامل مع تسوية بموافقة | جدول Stocktake منفصل، الفروقات تمر بنفس Approval Matrix |
| 20 | التقارير | أساسية أولًا، BI متقدم كمرحلة تالية | طبقة تحليلية منفصلة تُبنى فوق نفس الجداول التشغيلية دون تعديلها |
| 21 | التنفيذ | بناء مخصص بالكامل (Full Custom) | لا اعتماد على ERP جاهز (مثل Odoo)؛ الفريق يملك الكود بالكامل |

## ملاحظات مهمة لأي مطوّر يكمل على هذا المستودع

- **لا تبسّط تتبع الدفعات (Batch/Lot).** حتى لو بدأت بـ Weighted Average لكل الأصناف، الجداول
  يجب أن تدعم الدفعات من اليوم الأول لأن القرار #9 يسمح بالتبديل لاحقًا لكل صنف على حدة، وأيضًا
  لأن تواريخ الصلاحية تعتمد على تتبع الدفعات بغض النظر عن طريقة التقييم.
- **لا تبني Approval كـ if/else داخل كود الـ PO.** يجب أن تكون قواعد قابلة للتعديل من لوحة تحكم
  إدارية بدون تعديل كود (انظر القرار #8).
- **لا تفترض أن كل Order له طاولة أو قناة واحدة ثابتة.** حقل channel وحقل table كلاهما اختياري
  ومرن من اليوم الأول (القرارات #10 و#13).
