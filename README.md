# Restaurant ERP — نظام تشغيل سلسلة مطاعم متكامل

نظام مخصص (Full Custom) يربط الكاشير بالمبيعات والإنتاج والمشتريات والمخزون في دورة واحدة متكاملة،
لسلسلة فروع بعلامة تجارية واحدة تتضمن مطبخ مركزي (Central Kitchen) وفروع (Branches).

هذا المشروع تحت البناء المرحلي — راجع `docs/DECISIONS.md` للقرارات المعمارية الكاملة،
و`docs/ARCHITECTURE.md` لخطة التنفيذ المرحلية (Roadmap).

  حقيقية، اللوحة الإدارية ملف HTML ثابت واحد بلا أي أداة بناء، فالحل هنا **طابور مزامنة عام** بدل

  تلقائيًا عند فشل الشبكة (لا فرق بين قراءة وأخرى -- كل شاشات اللوحة العشرة تستفيد بلا أي تعديل
  في أي دالة منها لأنها كلها تمر بدالة `api()` نفسها)، وأي طلب POST/PATCH/DELETE يفشل بفشل شبكة
  حقيقي (`TypeError` من `fetch()`، **وليس** رفضًا حقيقيًا من السيرفر كـ 400/403 -- نفس تمييز
  `isNetworkError` المستخدم في `apps/pos-web/src/api/client.ts`) يُحفظ في طابور Dexie ويُعاد
  تشغيله تلقائيًا بنفس ترتيبه عند عودة الاتصال (أو كل 20 ثانية كشبكة أمان، نفس عادة
  `syncEngine.ts`). **حد صريح ومقصود في النطاق**: لأن الطابور عام (مسار+طريقة+محتوى، لا نوع
  عملية محدد)، لا يوجد دمج تفاؤلي تلقائي للنتيجة داخل قوائم الكاش المعروضة -- العملية المعلَّقة
  تُعرض عبر شريط تنبيه عام ("🔌 غير متصل...") ورسالة الخطأ الموجودة أصلًا في كل دالة (نفس نمط
  `catch (e) { flashGlobal('❌ ' + e.message, 'err'); }` الموجود بالفعل في كل مكان)، وتظهر فعليًا
  في القائمة فقط بعد نجاح المزامنة الحقيقية -- تبسيط متعمَّد بدل دمج تفاؤلي خاص بكل مورد من
  الموارد العشرة، لا نقص غير موثَّق. مكتبة Dexie نفسها **مُضمَّنة محليًا** (`prototypes/dexie.min.js`
  عبر npm لا CDN) حتى لا تعتمد قدرة "العمل بدون اتصال" نفسها على الوصول لخادم خارجي أول مرة تُفتح
  فيها الصفحة. `prototypes/service-worker.js` (مكتوب يدويًا، لا `vite-plugin-pwa` لعدم وجود أداة
  بناء) يخزّن غلاف التطبيق فقط (الصفحة + `dexie.min.js`) بحيث تُفتح الصفحة فعليًا حتى بلا اتصال
  إطلاقًا من أول مرة (مؤكَّد بتنقّل جديد كامل بمتصفح حقيقي بعد قطع الاتصال، لا مجرد بقاء الجلسة
  الحالية شغالة) -- لا يتدخل إطلاقًا في طلبات الـ API الحقيقية. مُتحقَّق منه فعليًا عبر Playwright
  حقيقي (`context.setOffline(true)`): قراءة من الكاش أثناء الانقطاع، كتابة (إنشاء فرع) تُحفظ في
  الطابور بدل الضياع، ثم عند عودة الاتصال تُعاد المحاولة فعليًا وتصل للـ API الحقيقي (تأكيد
  باستعلام مباشر لا مجرد إفراغ الطابور محليًا)، وفتح الصفحة من الصفر بلا اتصال إطلاقًا.
- المتبقي: الرفع الفعلي لـ ZATCA (بمجرد توفر بيانات اعتماد حقيقية) هو الشيء الوحيد المؤجَّل من كل
  خطة التنفيذ الأصلية — راجع `docs/ARCHITECTURE.md` للتفاصيل الكاملة لكل مرحلة، ولاقتراحات ما بعد
  خطة التنفيذ الأصلية.

## النشر أونلاين (Render)

`render.yaml` (Blueprint جاهز في جذر المستودع) ينشر النظام كامل بثلاث خدمات: قاعدة بيانات
PostgreSQL مُدارة (`restaurant-erp-db`)، الـ API (`restaurant-erp-api`، NestJS)، ولوحة التحكم
(`restaurant-erp-admin`، static site لملف `prototypes/admin_panel.html`).

**الخطوات**:
1. من لوحة Render: **New +** → **Blueprint** → اربط مستودع GitHub هذا (`accabdullahismail1991-lgtm/restaurant-erp`).
2. Render يكتشف `render.yaml` تلقائيًا ويعرض الخدمات الثلاث -- اضغط **Apply**.
3. (اختياري، قبل أول Deploy لو حابب): من إعدادات خدمة `restaurant-erp-api` أضف متغيرات البيئة
   `ADMIN_PHONE`/`ADMIN_PASSWORD` لو عايز حساب مدير مختلف عن الافتراضي المحلي. لو سبتهم فاضيين،
   هيتزرع نفس حساب التطوير المحلي (`+966500000000` / `ChangeMe123!`) -- **غيّره فور أول دخول لو
   النظام هيتفتح لأي حد تاني غير فريق التطوير**، لأن تعديل هذه المتغيرات بعد إنشاء المستخدم لأول
   مرة لن يغيّر كلمة سره (`seed.ts` upsert لا يعدّل مستخدمًا موجودًا بالفعل).
4. بعد اكتمال الـ Deploy (دقيقتين تقريبًا لأول مرة): افتح رابط `restaurant-erp-admin`
   (شكله `https://restaurant-erp-admin.onrender.com/admin_panel.html` -- تأكد من الاسم الفعلي في
   لوحة Render لو Render أضاف لاحقة لتفادي تعارض اسم)، وفي حقل "عنوان الـ API" أول مرة الصق رابط
   خدمة `restaurant-erp-api` (شكله `https://restaurant-erp-api.onrender.com`) -- يُحفظ تلقائيًا في
   المتصفح (localStorage) فلن تحتاج تكتبه كل مرة.
5. سجّل الدخول بحساب المدير (الافتراضي أو اللي حددته في الخطوة 3).

**ملاحظات صريحة**: الخطة المجانية على Render "تنام" الخدمة بعد فترة خمول فتأخذ أول طلب بعدها ثوانٍ
لتنهض -- طبيعي، ليس عطلاً. `prisma migrate deploy` + بذر البيانات (`prisma:seed`، آمن تمامًا يتكرر
لأنه upsert بالكامل) يعملان تلقائيًا عند كل تشغيل للخدمة، فليس هناك خطوة يدوية بعد أول نشر. لو
احتجت تشغيل أمر لمرة واحدة يدويًا (فحص بيانات، إلخ) استخدم تبويب **Shell** في لوحة تحكم خدمة الـ API.

## كيف تكمل من هنا (باستخدام Claude Code)

1. **خطة التنفيذ الأصلية اكتملت بالكامل (المراحل 0-11)**: كل الوحدات التشغيلية (1-7 + الجرد)،
   واجهة كاشير React حقيقية مع دعم العمل بدون اتصال (`apps/pos-web`، Phase 8)، توليد/توقيع فاتورة
   ZATCA محليًا عند كل دفع (Phase 9، `apps/api/src/zatca/`)، KDS+Promotions+CRM/Loyalty (Phase 10،
   `src/kitchen/`+`src/promotions/`+`src/customers/`)، وأخيرًا طبقة BI/Analytics للقراءة فقط
   (Phase 11، `apps/api/src/analytics/`: ملخص مبيعات، أصناف أكثر مبيعًا، تكلفة طعام حقيقية من
   تكلفة الدفعات الفعلية المُستهلَكة، تقييم مخزون، تنبيهات نقص).
2. **الشيء الوحيد المؤجَّل من كل خطة التنفيذ الأصلية**: الرفع الفعلي لفاتورة ZATCA لمنصة فاتورة
   (Phase 9) -- يحتاج شهادة CSID حقيقية من تسجيل/OTP عبر بوابتهم، لا يمكن الحصول عليها آليًا من
   أي بيئة تطوير. إن توفرت بيانات اعتماد حقيقية لاحقًا، فعّلها في `ZatcaService.submitToZatca`
   (التعليق هناك يشرح بالضبط الثلاث خطوات اللازمة).
3. **أي عمل تالٍ الآن هو تكرار جديد فوق أساس مستقر، لا استكمال لمرحلة ناقصة**. تكراران من هذه
   مبنيان فعلًا الآن: **تقارير مجدولة + تصدير Excel/PDF** (`apps/api/src/reports/`) و**العمل بدون
   اتصال للوحة التحكم** (`prototypes/admin_panel.html` + `prototypes/service-worker.js`) -- انظر
   قسم "الحالة الحالية" أعلاه للتفاصيل والقيود (Excel/PDF: Excel هو الصيغة الصحيحة عربيًا بالكامل؛
   العمل بدون اتصال: طابور مزامنة عام لا دمج تفاؤلي لكل مورد). أمثلة معقولة تانية لسه ما اتبنتش:
   لوحات تحكم تفاعلية أعمق، BOGO/COMBO الحقيقيان في محرك العروض (`src/promotions/`)، دمج استبدال
   نقاط الولاء تلقائيًا في الطلب بدل تطبيقه يدويًا (`src/customers/`)، أو split-bill/دمج طاولات
   (القرار #13، غير مبني بعد).
4. لا تبدأ بكل الوحدات دفعة وحدة — كل وحدة يجب أن تُبنى وتُختبر (باختبارات e2e حقيقية، مو Unit
   tests وهمية فقط) قبل الانتقال للتالية، بنفس نمط المراحل 1-7.
5. اتبع نفس نمط RBAC المستخدم في المراحل السابقة (`@RequirePermission('code')` + `PermissionsGuard`
   يقرأ من قاعدة البيانات مباشرة، مو من الـ JWT) لأي Endpoint جديد يحتاج صلاحية، ونمط الـ Scope
   المشترك في `src/common/location-scope.util.ts` لأي مورد مرتبط بموقع.
6. `InventoryService` (استلام/خصم FIFO/متوسط تكلفة مرجّح/عكس استهلاك)، `src/common/location-scope.util.ts`،
   و`ApprovalRulesService.findApplicableRule` (مصفوفة الموافقات، تدعم أي `documentType` الآن --
   جدول `Approval` نفسه بقى عامًا بحقل FK اختياري لكل نوع مستند) كلها مبنية كوحدات مشتركة
   يُعاد استخدامها -- لا تكرّر منطقها في أي وحدة قادمة.
7. **لأي اختبار e2e جديد**: استخدم `test/reset-db.ts`'s `resetDatabase(prisma)` في بداية
   `beforeAll` بدل تنظيف يدوي جدول-جدول -- تنظّف كل الجداول التشغيلية من كل الوحدات المبنية دفعة
   واحدة (children قبل parents)، لأن كل ملفات `*.e2e-spec.ts` تشتغل بنفس عملية Jest
   (`--runInBand`) بترتيب أبجدي ضد نفس القاعدة، وأي جدول جديد له FK على جدول قديم غير محدث فيها
   هيكسر تنظيف ملف اختبار تاني.

## التقنيات

| الطبقة | التقنية |
|---|---|
| Backend API | Node.js + TypeScript + NestJS |
| قاعدة البيانات | PostgreSQL + Prisma ORM |
| المصادقة | JWT (access 15m + refresh 7d)، RBAC مرن بجدول Role/Permission، Scope على مستوى الموقع |
| Frontend (الكاشير) | React + Vite + TypeScript -- PWA حقيقي (`apps/pos-web`): IndexedDB (Dexie) + Sync Queue + Service Worker، مبني ومُختبر أونلاين وبدون اتصال |
| الحاويات | Docker Compose للتطوير المحلي (اختياري -- سيرفر PostgreSQL محلي يعمل بنفس الكفاءة) |
